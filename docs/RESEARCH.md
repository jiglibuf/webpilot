# Исследование и технические решения

Документ описывает, как выбирались библиотеки и архитектура, какие гипотезы проверялись
экспериментально и почему в итоге получилось то, что получилось. Числа в таблицах — реальные
замеры (`scripts/measure_perception.py`, артефакт `docs/measurements.json`).

## 0. Как формулировалась задача

Требования задания декомпозированы в проверяемый список:

| Требование | Как закрыто в коде | Как проверяется |
|---|---|---|
| Программное управление браузером | Playwright, `browser/session.py` | `tests/test_browser_session.py` |
| Persistent sessions (ручной вход → агент продолжает) | `launch_persistent_context(user_data_dir)`, тот же профиль между запусками | `tests/test_browser_session.py::test_profile_persists_cookies` + демо |
| Видимый браузер | `Config.headless=False` по умолчанию, headful launch | демо-видео |
| Автономность, многошаговость | `agent/loop.py` (observe → decide → act → verify до `finish`) | `tests/test_loop.py` |
| Модели Claude/OpenAI | `llm/anthropic_provider.py`, `llm/openai_provider.py` | `tests/test_llm_providers.py`, live-тесты |
| Управление контекстом (нельзя пихать страницу целиком) | снайфер + `agent/memory.py` | замеры ниже, `tests/test_memory.py` |
| ≥1 продвинутый паттерн | реализованы **все три**: sub-agents, error handling, security layer | `tests/test_subagents.py`, `tests/test_loop.py`, `tests/test_policy.py` |
| Никаких заготовок действий и хардкода селекторов/подсказок | элементы адресуются только целочисленным `id` из снапшота; промпты без сайтов и шагов | `grep`-тесты против хардкода в `src/` |

## 1. Автоматизация браузера: Playwright vs Selenium vs Puppeteer vs «агентные» обёртки

Критерии: видимый persistent-браузер, ожидание сети/локаторов из коробки, работа с iframe,
shadow DOM, несколькими вкладками, диалогами, CDP для снапшотов, Python-стек (модели и
склейка удобнее, чем Node).

* **Playwright** — выбран. `launch_persistent_context` даёт ровно то, что просят в задании
  (ручной логин живёт в профиле), авто-ожидания уменьшают количество «пустых» действий,
  есть CDP-сессия для accessibility-дерева, единый API для вкладок/фреймов/диалогов.
* **Selenium** — persistent-сессия достижима (user-data-dir), но ожидания, фреймы и
  диалоги требуют ручного кода, а CDP-доступ беднее.
* **Puppeteer** — то же, что Playwright, но Node-экосистема и нет встроенного
  headful-профиля «в один вызов»; весь агентный слой пришлось бы писать на TS.
* **Готовые агентные обёртки (browser-use, Stagehand, Claude for Chrome)** — рассмотрены и
  отклонены как основа: задание проверяет умение построить агента, а не подключить SDK;
  но их архитектуру (индексация интерактивных элементов, «снапшот вместо HTML») я изучил и
  воспроизвёл.

## 2. Провайдер и SDK

* Единый интерфейс `LLMClient` + две нативные реализации: **OpenAI** (`chat.completions` с
  `tools`) и **Anthropic** (Messages API, `tool_use`/`tool_result` блоки). Плюс
  `LocalProvider` для локальных моделей (Ollama, vLLM, llama.cpp, LM Studio) через
  OpenAI-совместимый `/v1`.
* Прямые HTTP-вызовы вместо SDK отклонены: SDK дают идемпотентные ретраи, нормализацию
  ошибок и типизированный usage-объект, который нужен для учёта токенов.
* Локальные модели поддержаны как первоклассный провайдер: задание явно разрешает
  локальный инференс, и вся агентная логика не зависит от вендора. Демо записано на
  OpenAI-совместимом эндпоинте (DeepSeek), потому что качество многошагового
  tool-calling у маленьких локальных моделей пока недостаточно для честного демо —
  это проверено отдельными прогонами.

## 3. Как смотреть на страницу: главный эксперимент

Гипотеза: «отправить HTML в модель» не вариант (задание прямо запрещает). Проверил четыре
стратегии восприятия на реальных страницах (`scripts/measure_perception.py`, headless
Chromium, оценка токенов по chars/3.9 для латиницы):

| Страница | сырой HTML | видимый текст | accessibility tree (CDP) | интерактивные элементы (наша схема) |
|---|---|---|---|---|
| saucedemo.com (форма логина) | 700 | 41 | 231 | 44 |
| books.toscrape.com (каталог) | 13 074 | 520 | 4 924 | 504 |
| en.wikipedia.org/wiki/Web_browser | 158 957 | 5 241 | 24 516 | 5 121 |
| локальный тест-магазин (главная) | 730 | 95 | 409 | 40 |

Выводы:

1. **Сырой HTML дороже в 16–56 раз** и при этом хуже по сигналу: 90 % токенов — разметка,
   стили и скрипты, а не то, что можно нажать. Стратегия отброшена.
2. **Accessibility tree** компактнее HTML (в ~5–7 раз), но остаётся большим (24 k токенов на
   средней статье) и содержит много бесполезных узлов; к тому же в нём нет *адресуемости*:
   из узла дерева не следует, как по нему кликнуть.
3. **Интерактивные элементы** (кнопки/ссылки/поля + их доступные имена) — самый маленький и
   самый действенный сигнал (40–500 токенов), и он сразу даёт **стабильный числовой `id`**,
   которым агент адресует действие. Это и стало основой снайфера
   (`browser/dom_snapshot.js`): на каждом снимке страницы интерактивным узлам присваивается
   `data-webpilot-id=n`, и модель оперирует только этими id — селекторы в коде физически
   отсутствуют.
4. **Текст страницы** нужен для ответов на вопросы, но не целиком: он ранжируется
   (алерты → заголовки и видимая область → остальное) и обрезается до бюджета.
5. **Скриншоты + vision** не используются как основной канал: дороже по токенам, медленнее и
   не даёт адресуемости. Скриншоты сохраняются как артефакт для человека/аудита, а
   выборочный доступ к «сырому» тексту отдан субагенту-экстрактору.

Итоговое восприятие агента = компактный снапшот (элементы + алерты + ранжированный текст +
скролл/вкладки/ошибки консоли) в пределах бюджета ≈2.6 k токенов, при необходимости —
дельта от предыдущего снапшота.

## 4. Управление контекстом

Реализованные (и независимо тестируемые) стратегии:

1. **Компактный снапшот вместо HTML** — 16–56-кратное сокращение (замеры выше).
2. **Бюджет на страницу**, который ужимается по мере роста истории (2 600 → 700 токенов),
   при переполнении в первую очередь отбрасываются элементы вне вьюпорта (счётчик
   `dropped_elements` честно показывает потери).
3. **Дельта-режим**: один раз страница отправляется целиком, дальше — только изменившиеся
   элементы (`mode="delta"`).
4. **Скользящее окно шагов** (последние N — дословно) + **свёртка старых шагов** в
   «эпизодический конспект» субагентом-summarizer'ом, с детерминированным фолбэком.
5. **Скрэтчпад (`notes`)** — заметки, которые агент ведёт сам и которые всегда в контексте,
   поэтому переживают любую компакцию.
6. **Дедупликация повторных состояний**: тот же хеш страницы → «page unchanged since step N»
   вместо повторного дампа.
7. **Обрезка результатов инструментов** до ~350 токенов и защита от циклов (одинаковая
   подпись действия + тот же хеш страницы трижды → жёсткое предупреждение модели).
8. **Учёт токенов по факту** (provider usage) + оценка `count_tokens` до отправки, чтобы
   решение о компакции принималось до переполнения окна.

## 5. Продвинутые паттерны

* **Sub-agent architecture.** Экстрактор читает «сырой» текст/HTML страницы в своём
  контексте с большим бюджетом и возвращает только ответ + цитату-доказательство; отчёты о
  падениях уходят в recovery-субагента, который предлагает альтернативные действия; свёртку
  истории делает summarizer. Основной цикл видит только компактные результаты — изоляция
  контекста вместо его раздувания.
* **Обработка ошибок.** Каждое действие верифицируется (URL/хеш страницы/значение поля
  до и после); «ничего не изменилось» → структурированный отказ с диагностикой
  (элемент перекрыт оверлеем / disabled / форма отвергла значение) и подсказкой; ретраи с
  эскалацией в recovery-субагента; детект циклов по хешу страницы; деградация до честного
  частичного ответа вместо выдуманного успеха.
* **Security layer.** Детерминированный движок правил классифицирует действия **по смыслу**
  (оплата/заказ, удаление, отправка сообщений, изменение аккаунта, ввод пароля, загрузка
  файлов), а не по сайту: правила оперируют ролью/именем элемента, типом поля, URL и текстом
  страницы, поэтому работают на незнакомом сайте. Деструктивные действия требуют
  подтверждения человека в терминале (`--confirm-mode ask|allow|deny`,
  `--auto-approve-domain`), всё пишется в append-only JSONL-аудит с редактированием секретов.
  Поля пароля не заполняются автоматически: агент обязан попросить человека войти вручную —
  persistent-профиль сохранит сессию.

## 6. Что сознательно не сделано

* Нет ни одного жёстко прописанного селектора (`a[data-qa=...]`), нет списков шагов под
  конкретную задачу, нет знания про конкретные сайты (проверяется grep-тестами).
* Нет «reflection-циклов на каждый шаг» (voting/self-consistency) — это удорожает прогон
  втрое при небольшом выигрыше; вместо этого дешёвая верификация состояния и recovery по
  факту ошибки.
* Нет OCR/vision-канала для капчи: обход капчи не является задачей, а решение через
  «спросить человека» честнее.

## 7. Проверка

* `pytest -q` — офлайн-набор (без сети и ключей): снайфер и рендер страницы, провайдеры на
  canned-JSON, политика безопасности (включая false positives), контекст-менеджер под
  нагрузкой, цикл агента на стаб-исполнителе и scripted-модели, CLI.
* `pytest -m live` — smoke-тесты живых провайдеров (нужны ключи).
* `scripts/measure_perception.py` — замеры выше, воспроизводимы.
* End-to-end демо на публичном тест-магазине и на локальном тест-сайте — см.
  `docs/DEMO.md` и записанное видео.
