# Как запустить и посмотреть, как это работает

Инструкция для того, кто хочет **увидеть** агента в деле: окно браузера с одной стороны, живой
трейс с другой. Занимает минут пять, ключ нужен только для живого прогона.

## 1. Что нужно

* Linux или macOS, Python 3.11 (в инструкции — `uv`, но подойдёт любой venv);
* браузер Chromium от Playwright (`make install-browsers` поставит его локально);
* ключ одного из провайдеров: OpenAI, Anthropic, DeepSeek/OpenRouter или локальная модель с
  OpenAI-совместимым `/v1` (Ollama, vLLM, llama.cpp, LM Studio). Для локальной модели ключ не нужен.

```bash
git clone https://github.com/jiglibuf/webpilot.git && cd webpilot
make install                 # .venv + пакет + dev-зависимости
make install-browsers        # Chromium для Playwright
cp .env.example .env         # впишите ключ нужного провайдера
```

## 2. Самый предсказуемый прогон: локальный тест-магазин

Ничего внешнего не нужно, сеть не используется, поведение детерминировано.

```bash
# терминал №1 — тест-магазин на http://127.0.0.1:8765
make serve-shop

# терминал №2 — агент
webpilot "Открой http://127.0.0.1:8765/ , найди самый дорогой товар, положи его в корзину и назови итоговую сумму"
```

Что вы увидите:

1. Откроется **видимое окно Chrome** (не headless) и постоянный профиль `~/.webpilot/profile`.
2. В терминале пойдёт **трейс**: какой инструмент вызван, с какими аргументами, что изменилось на
   странице, сколько токенов ушло, какие риски сработали.
3. Агент сам найдёт каталог, сравнит цены, нажмёт «в корзину», откроет корзину и назовёт сумму.
   Плана шагов у него нет — вы увидите, что он «думает» по странице, а не по сценарию.

Короткий вариант той же команды — `make demo-local` (сам поднимает магазин и запускает агента).

## 3. Публичный сайт с ручным логином (как в записи)

Persistent session нужен ровно для этого случая: пароль вводит **человек**, агент продолжает
работу в той же сессии.

```bash
webpilot --profile-dir ~/.webpilot/demo-profile --max-steps 60 \
  "Зайди на https://www.saucedemo.com/ и войди: логин standard_user. Пароль вводит человек. \
   Затем оформи заказ на Backpack и Bike Light на имя Test User, индекс 12345, и назови итоговую сумму."
```

Как проходит ручная часть:

1. Агент открывает страницу, вводит логин и **останавливается** — поля пароля он не заполняет
   никогда. В терминале появляется вопрос вида «введите пароль в поле Password на странице,
   сообщите, когда готово — я нажму Login».
2. Вы печатаете пароль в окне браузера (именно вы, руками).
3. Возвращаетесь в терминал и отвечаете на вопрос — например `готово`. На приглашении
   `answer (Enter to skip)>` можно и просто нажать Enter: это «ответа нет», агент пойдёт сам
   проверять, что получилось на странице.
4. Дальше агент идёт сам. Перед оплатой он остановится ещё раз: в терминале появится панель
   подтверждения с причиной (`pay.action` — «начинает оплату, деньги могут уйти со счёта»).
   Ответ `y` — продолжаем, `n` — агент вернётся к странице и попробует другой путь.

Вход сохраняется в профиле, поэтому следующий запуск с тем же `--profile-dir` логин уже не спросит.

## 4. Другие сайты

Настройки под конкретный сайт в проекте нет и быть не должно: агенту нужен только URL в
задаче, а структуру страниц он разбирает сам — нумерует интерактивные элементы и решает по
состоянию, а не по знанию сайта. То, что действительно стоит настроить:

| Что | Как | Зачем |
|---|---|---|
| Свой профиль на сайт | `--profile-dir ~/.webpilot/<сайт>` | логины сохраняются между прогонами, сессии разных сайтов не путаются |
| Шагов побольше | `--max-steps 60` | длинные сценарии (поиск → фильтры → корзина → оформление) |
| Страница поменьше | `--page-budget 1500` | очень большие каталоги и лонгриды |
| Доверенный домен | `--auto-approve-domain shop.example.com` | на своём тестовом сайте не подтверждать каждый шаг оформления |
| Совсем без спроса | `--confirm-mode yolo` | см. следующий раздел |
| Без окна | `--headless` | CI, медленная машина, отладка |

Задачи, на которых проверено (все три реально проходили):

```bash
# 1. локальный тест-магазин — без сети вообще
make serve-shop                  # в отдельном терминале
webpilot "Открой http://127.0.0.1:8765/ , найди самый дешёвый товар, положи его в корзину и скажи сумму"

# 2. публичный сайт без входа: анализ каталога
webpilot "На https://books.toscrape.com/catalogue/category/books/travel_2/index.html скажи, сколько книг в категории Travel и у скольких рейтинг 5 звёзд"

# 3. сайт с обязательным входом — пароль вводит человек
webpilot --profile-dir ~/.webpilot/sauce --max-steps 60 \
  "Зайди на https://www.saucedemo.com/, войди как standard_user (пароль вводит человек: спроси меня    через ask_user). Затем положи в корзину Sauce Labs Backpack и Sauce Labs Bike Light, оформи заказ    на Test User, индекс 12345, и назови итоговую сумму"
```

Если сайт не поддаётся — смотрите трейс: у каждого отказа есть причина (`element covered`,
`disabled`, `no effect`, `form rejected the value`), а не просто «не получилось».

## 5. Режим yolo: совсем без подтверждений

По умолчанию агент спрашивает перед каждым деструктивным действием — на длинном оформлении
заказа это несколько остановок подряд. Если прогон черновой (свой тестовый сайт, локальный
магазин, отладка), подтверждения можно снять:

```bash
webpilot --confirm-mode yolo "задача"
WEBPILOT_CONFIRM_MODE=yolo webpilot "задача"     # то же через окружение
```

Что при этом происходит и что не происходит:

* вопросы `y/N` не задаются вообще — ни на оплату, ни на удаление, ни на отправку;
* в шапке прогона режим печатается **красным** (`yolo — no confirmations…`), чтобы его нельзя
  было включить незаметно;
* в аудите каждое такое решение помечается `auto_approved_yolo` — видно, что человека в цикле
  не было (в отличие от `approved_by_human`);
* **пароль всё равно вводит человек**: это отдельное правило, а не подтверждение, и оно
  проверяется раньше режима. Тест `test_yolo_mode_still_refuses_password_fields` следит за этим;
* `--confirm-mode deny` (запрещать всё деструктивное) работает как раньше — удобно, когда
  нужно посмотреть, как агент ищет обходной путь.

Мягкая альтернатива yolo — доверять только конкретному домену:
`--auto-approve-domain shop.example.com`.

## 6. Управление во время работы

| Действие | Что делает |
|---|---|
| `\t` | статистика: шаги, токены, сколько срезала компакция контекста |
| `\q` | мягкая остановка — агент завершает честным отчётом о том, что успел |
| `\s` | пропустить действие, которое вот-вот выполнится |
| `\h` | помощь по горячим клавишам |
| любой текст | уходит агенту как дополнительная инструкция перед следующим шагом |
| `y` / `n` | ответ на панель подтверждения деструктивного действия |
| Enter на `answer (Enter to skip)>` | «ответа нет» — агент продолжает сам |

Полезные флаги: `--headless` (без окна), `--max-steps N`, `--confirm-mode ask|allow|yolo|deny`,
`--auto-approve-domain shop.example.com` (для своего тестового домена), `--page-budget N`,
`--context-budget N`, `--profile-dir DIR`, `-v`. Полный список — `webpilot --help`.

## 7. Куда смотреть после прогона

* `~/.webpilot/transcripts/*.jsonl` — полный транскрипт: каждый шаг, аргументы, результат
  верификации, расход токенов (`RunResult.usage.main` / `.subagents`).
* `~/.webpilot/audit.jsonl` — append-only аудит решений риск-движка, включая подтверждения и
  отказы (секреты вырезаются).
* `~/.webpilot/screenshots/` — снимки экрана, если не отключены флагом `--no-screenshots`.

## 8. Записать такое же видео

```bash
python demo/record_demo.py --task "…та же задача…" --extra-args "--max-steps 60" \
  --out demo/out/demo.mp4 --takes 2
```

Харнесс поднимает **отдельный X-дисплей** (рабочему столу не мешает), кладёт терминал и браузер
рядом, сам отыгрывает роль человека — вводит пароль и подтверждает опасное действие — и пишет
видео. `--takes N` делает несколько дублей и оставляет успешный. Для VP9/WebM укажите имя файла с
`.webm` (H.264 в Fedora может быть недоступен — см. README, раздел про форматы видео).

```bash
python demo/record_demo.py --help      # все ключи
```

## 9. Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `provider … requires an API key` | ключ не найден: заполните `.env` или задайте переменную окружения провайдера |
| Окно браузера не появилось | запущено с `--headless` или переменной `WEBPILOT_HEADLESS=1` |
| `port 8765 is in use` | тест-магазин уже запущен — остановите прошлый `make serve-shop` |
| Агент пишет «no effect» | страница не отреагировала: в трейсе будет причина (перекрыт, `disabled`, форма отклонила значение); executor уже пробует нативный путь и фолбэк внутри страницы |
| Локальная модель отвечает мусором | слабые модели плохо держат формат tool-calling; возьмите модель от 14B или облачный провайдер |
| Нужно понять, доходит ли ввод до страницы в вашем окружении | `make probe-input` |

## 10. Офлайн-проверка без ключей

```bash
make test          # >500 тестов: снапшот, провайдеры на canned-JSON, политика, контекст, цикл, CLI
make measure       # пересобрать замеры восприятия страниц
make probe-input   # проверить доставку синтетического ввода в этом окружении
```
